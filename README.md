from real MovieLens interaction histories), trained and evaluated against a

## MDP Formulation Summary

- **State**: user genre-preference profile (built from the user's training
  history), a short rolling window of the genres of the last 3 recommended
  movies (so the agent can track and avoid over-repeating a genre), and the
  normalised step count within the episode. 77 dimensions in total.
- **Action**: Discrete(200) -- pick one of the 200 most-rated movies in the
  training data to recommend next. Already-recommended movies within the
  same episode are excluded via action masking.
- **Reward**: `(rating - 3) / 2` if the simulated user actually rated the
  recommended movie in the relevant split of their real history; `-0.1` if
  the user never rated it (insufficient signal to reward); `-1.0` for
  repeating an already-recommended movie in the same episode.
- **Episode length**: 10 recommendations (or fewer if the candidate pool is
  exhausted first) -- truncation, not natural termination, since there is no
  terminal/absorbing state in this task.
- **Discount factor**: 0.95, reflecting the short (10-step) effective horizon.
- **Markov property**: does NOT fully hold under this state representation
  -- the genre-preference profile is a static summary of the user's training
  history and does not update within the episode based on which
  recommendations were accepted or ignored (MovieLens is offline log data,
  not an interactive user simulator, so there is no observed "reaction" to
  compensate with). This is stated explicitly as a limitation below and in
  the report.

## Baselines

- **Popularity-based**: always recommends the next most-rated (in training
  data) movie the user hasn't been recommended yet in this episode.
- **Item-based collaborative filtering**: recommends the candidate movie
  with the highest cosine similarity (on the training user-item rating
  matrix) to the movies the current user rated highly in training.

Both baselines are evaluated through the exact same `eval_harness.py` code
path, on the same held-out users/seeds/episodes, as the DQN agent.

## Data Quality Checks (see notebook, Sections 2b-2d)

Before training, the notebook performs and documents:
- **EDA**: rating distribution, ratings-per-user and ratings-per-movie
  distributions (justifying the 20-rating user filter and 200-movie
  candidate cutoff), and genre frequency (justifying tracking diversity as
  a separate metric).
- **Data cleaning checks**: 0 duplicate ratings, 0 missing values in either
  file; 34 movies with `"(no genres listed)"` identified and their handling
  (an all-zero genre vector) made explicit.
- **Train/test split verification**: independently re-derives the
  chronological per-user split from raw timestamps and confirms 0 of 525
  usable users show any temporal leakage between their train and test
  interactions.

## Results Summary

Across two independent runs (3 seeds/60k timesteps, then 5 seeds/120k
timesteps as the final, reported configuration), the same qualitative
pattern replicated:

- **No distinguishable accuracy advantage over the baselines.** DQN's
  cumulative reward, hit rate, precision@k, and NDCG@k all overlap
  substantially with both Popularity and Item-CF once seed variance is
  accounted for; in the final run, DQN's point estimates for hit rate and
  NDCG@k were marginally below Popularity's. Given this overlap, DQN is
  **not** claimed to beat the baselines on accuracy.
- **A consistent, replicated diversity advantage.** DQN's intra-list
  diversity (0.760 +/- 0.004 in run 1; 0.742 +/- 0.010 in run 2) was
  clearly and consistently higher than both Popularity (~0.65) and Item-CF
  (~0.62-0.625) in both runs, with no overlap in either.
- The training curve shows a sharp early dip (down to roughly -2.8 reward)
  coinciding with the epsilon-greedy exploration-decay period, followed by
  recovery and a stable plateau reached well before the training budget was
  exhausted -- indicating the setup converged rather than being
  undertrained.

Full discussion of these results, including likely causes (the static
per-episode state representation, and the size of the action space relative
to available reward signal) is in the project report.
